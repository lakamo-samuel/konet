# Account and provider settings

`/settings` uses live current-user and university directory queries. Profile edits send changed canonical fields only to `PATCH /me/profile`: `fullName`, `avatarUrl`, `universityId`, `campusId`. Campus options use backend IDs rather than labels. Changing affiliation requires an explicit acknowledgment that student verification and provider approval/publication reset; backend obligations and directory validation remain authoritative. Profile pictures are uploaded directly to Cloudinary using a short-lived signed ticket from the backend, verified server-side, and saved with the other profile edits; users can replace or remove their picture on this page. JPEG, PNG and WebP images up to 5 MiB are accepted.

Email changes are separate from profile editing. The frontend requests a code with the new email and current password, tracks server-issued expiry/resend timestamps, and confirms the challenge with a six-digit code. The request acknowledges queued delivery, not confirmed receipt. New challenges supersede previous codes. Codes and passwords are not persisted in localStorage. Password inputs and mutation variables are cleared after requests complete. An expired code requires another request.

Password change requires the current password, a new password of at least eight characters and matching confirmation. Deactivation requires a reason and explicit acknowledgment. The UI explains retained records, disabled sign-in, hidden provider profile, outstanding-obligation restrictions and the absence of self-service reactivation.

Successful password changes, email confirmation and deactivation clear frontend HttpOnly session cookies, development bearer storage and TanStack account caches, then navigate to sign-in. Failed actions preserve the current session. Credential-action 401 responses are not automatically retried through token refresh. Backend revocation applies to all sessions. Lost responses can require a manual sign-in with the new credentials; the frontend does not claim an operation failed safely just because delivery was interrupted.

`/provider/settings` reads the owner-only profile, so paused/draft profiles remain accessible. The frontend sends changed title, bio, cover URL, response-time minutes and availability to `PATCH /me/provider-profile`. Title/bio/cover edits invalidate approval; availability and response-time updates retain it. Pending review and suspension disable editing. Pause/publish uses `/me/provider-profile/status` with backend approval checks. Public profile reads are not used to populate settings. Links lead to existing onboarding, services, earnings and payout-account screens.

The former `saveProfile`/`saveProvider` placeholder contracts and unsupported label mappings are removed. All mappings remain centralized in frontend data access, with one shared session-ending-command policy used by server cookie handling, browser token handling and cache invalidation. No migration or new credentials are needed. Email changes use existing Resend/outbox configuration.

Validation covers profile mapping, campus ID selection and verification reset, filtered privileged fields, paused private profile reads, publication/re-review rules, blocked obligations, wrong credentials, failed/successful code confirmation, revoked sessions and deactivation through disposable HTTP fixtures. A client-boundary test checks token clearing only on success and suppression of credential-action refresh retries. Actual browser interactions and configured Resend delivery remain deployment checks. Admin frontend stays deferred.

Completed checks: 54 production-cookie and 55 development-token HTTP checks (109 total), `test:settings-client`, `test:realtime`, frontend typecheck, lint and production build. No emails, payments, uploads or project account changes were made by these tests.
